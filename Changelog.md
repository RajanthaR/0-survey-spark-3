- **Optimized ZIP bundle generation to keep peak memory proportional to one CSV at a time** instead of the whole bundle. The client (`downloadZipBundle` in `src/routes/admin.tsx`) previously called `fflate.zipSync(Object.fromEntries(files.map((f) => [f.name, strToU8(f.csv)])), { level: 6 })`, which (a) materialized every per-survey CSV as a `Uint8Array` simultaneously, (b) returned the entire compressed archive as one contiguous `Uint8Array`, and (c) ran deflate on the main thread — peak heap ≈ 2× the bundle size, with a long blocking pause on big exports. Replaced with fflate's chunked streaming writer: a single `new Zip((err, chunk, final) => …)` accumulates emitted chunks into a `Uint8Array[]`, and each per-survey CSV is fed through an `AsyncZipDeflate(name, { level: 6 })` (compression runs off-main-thread in a worker). Files are pushed sequentially with `await new Promise((r) => setTimeout(r, 0))` between entries so React can paint the in-progress frame and the GC can reclaim the previous file before the next one is added. Crucially, after each `strToU8(f.csv)` the source string is dropped from the array (`files[i] = { name, csv: "" }`) so the large CSV string can be collected immediately rather than staying pinned until `zip.end()`. The final `new Blob(chunks, { type: "application/zip" })` holds the chunk array without re-copying — large blobs may be spilled to disk by the browser, so JS-heap usage no longer scales linearly with bundle size.
